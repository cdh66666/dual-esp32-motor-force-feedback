# 视频素材

README 第一节里自动循环播放的 7 段预览，以及它们是怎么压出来的。

## 素材是什么

每段都是**一次录制、一个进程、当场合成的双源画面**：

| 画面区域 | 来源 |
| --- | --- |
| 上半 | USB 实物相机（`2K Camera (1bcf:cb07)`） |
| 下半 | 调试台页面，100 Hz 遥测曲线 |
| 两半右上角 | **同一个时钟**，都以 `T+秒.毫秒` 烧进画面 |

所以暂停在任意一帧，都能直接对上「曲线在那一刻是什么样 / 电机在那一刻在做什么」。
录制端在后半段的板子握手、编码阶段不下发任何运动指令，手测片段全程只做记录。

## 为什么是 GIF，为什么是这个尺寸

GitHub 的 README 会过滤掉 `<video>`，**动图是唯一能在仓库首页自动播放并循环的格式**（动画 WebP 在 Safari 上会逐渐变成慢动作，不可用）。

原片是 1280×1528 / 15 fps，共 103 秒、约 75 MB —— 不适合随仓库长期托管。压缩按下表的顺序做，每一档都是「预览尺度下看不出来」的取舍：

| 手段 | 作用 |
| --- | --- |
| `fps=5` | 轴起转、曲线跳变在 5 fps 下依然看得出过程；15→5 直接去掉 2/3 帧 |
| `scale=400:-1:flags=area` | 盒式平均缩放。用 lanczos 会保留相机半边的传感器噪声，而噪声是 LZW 最不擅长的东西 |
| `atadenoise` | 时域平均。**这是收益最大的一档**：传感器噪声帧间不相关、曲线帧间高度相关，平均之后噪声没了、曲线还在 |
| `max_colors=32` + `bayer_scale=5` | 少颜色 + 粗抖动。细抖动是用字节换一个 400 px 下根本看不见的渐变 |
| `-loop 0` | 无限循环，这是放进来唯一的目的 |

结果：**103 秒 → 7.4 MB**（约 1/10），单段 0.7–1.8 MB。

```bash
# 重新生成（ffmpeg 用剪映自带的完整构建，系统 PATH 里没有）
python .workbuddy/scratch/camera/make_repo_gifs.py docs/videos --poster
```

参数在脚本顶部（`WIDTH` / `FPS` / `COLORS` / `BAYER` / `DENOISE`）。想更小就把 `WIDTH` 调到 360、`FPS` 调到 4；想更清楚就反过来，代价基本是线性的。

`meta/` 下是每段录制随原片一起落盘的 `meta.json`：逐帧墙钟、每条指令的发出时刻、以及判据用的 `verdict` 数据。README 和[验收页](../video-acceptance.html)里的每个数字都出自这里。

入库前只用 `scrub_meta_paths.py` 做过一处改写：录制机上的绝对路径（`outdir` / `video`）前缀换成 `<workdir>`，其余字段逐字节未动。

原始 15 fps 片段（`.webm`）体量大，留在开发机 `evidence/recordings/`，不进仓库；需要重新出片时用 `make_repo_gifs.py` 指向原片即可。
