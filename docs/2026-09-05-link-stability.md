## 1. 不能混淆的两类故障

- 12:09–12:10 的旧版电流测试：1.300/1.384 A 目标下触发 `encoder_stale`。其中一次保护停机后仍有 381 帧遥测。该事件不是固定 1 A USB 掉线，详见 [原诊断](2026-09-05-current-stop-diagnosis.md)。
- 12:25:48 的旋钮测试：最后一帧约 19.49 V、-166 mA、PWM 116、nFAULT=1、awake=1，随后无 RX。端口仍枚举，用户重复重连没有恢复；断电后直接查询也为零字节。这是真实的数据回包中断，不能用旧版保护停机解释。
- USB 1200-baud 控制请求仍能进入 ROM，说明恢复时控制通路尚能响应；不能据此推断所有 USB 层都正常，也不能凭现有记录认定电源、EMI 或 USB 栈中的唯一根因。

初始状态保存在 `evidence/flashing/20260905-122719-stability-start.json`。本轮没有要求用户再次物理重插，也没有擦除 NVS。

## 2. 实际修改

### 固件

1. 编码器读取独立调度为 1 kHz；速度计算仍为 500 Hz，位置 200 Hz，电流 2 kHz。到期时先读取，再检查数据新鲜度；读取前仍检查估算盲区位移，超过 150° 则停止，避免错误跨圈。以上为调度目标，不是带电全负载频率验收。
2. I2C 超时由 3 ms 改为 1 ms；累计读取次数、NACK、短读、拒收角度、读取耗时和主循环最大间隔。速度相关新鲜度保护保留，不是简单删除保护或统一放宽到 10 ms。
3. USB 发送泵最多每 1 ms 调用一次；FIFO 满时退出，避免紧循环反复 flush。队列积压时跳过新遥测，为回执/故障留空间；正常遥测仍是 100 Hz。
4. 增加 `LINK_STATS` 诊断。极端发送阻塞持续 1.5 s 时先休眠驱动，再进行有限次数的软件重启恢复；每次上电最多两次，不恢复旧目标或旧旋钮租约。该极端失效分支尚未进行注入测试，不能承诺任意 USB 硬件故障都可恢复。
5. 保留电流 PI、速度/位置参数与现有 R/Ke/方向/电流极性/扰动补偿标定。未提高电流限幅，未关闭 VM、nFAULT、编码器与看门狗保护。

### 后端与网页

- 按命令拒绝、保护故障、传输故障分类；链路异常使用一条持续可见的提示，真实保护故障仍可弹窗，同类弹窗去重，保留原始日志。
- 正常有回包的板执行 STOP/状态检查，不再为了保护恢复主动断开健康串口；只有真正无回包且用户明确点击恢复时才重建连接。
- 重建会话使用新会话 ID；旧目标、旧异步回执和旧续租不能重新启动电机。重新连接本身不唤醒驱动。
- 提供烧录维护状态，阻止网页自动连接争抢下载端口；新增仅限明确断电条件的 `tools/recover_usb_poweroff.py`。
- 源码另增加 HTTP 客户端关闭连接的正常异常处理，与串口错误分开。最后一次尝试重启后台加载这项小修补被执行策略拒绝，故这一个 HTTP 日志补丁待下次后台正常启动生效；此前的串口恢复、分类与维护逻辑已在本轮运行的后台中生效。

## 5. 尚未验收及下一步

本次完成的是断电恢复、源码修复、烧录、空闲 USB 压力测试与网页回归，**不是电机带电稳定运行验收，也未证明失联根因完全消除**。等待用户恢复电机电源后：

1. 先核对实时 USB 身份、母线、nFAULT、编码器与零电流，确认没有旧动作恢复。
2. 先做低电流短时正反转，再做低速连续变速与小角度保持；记录完整过程和结束后至少 10 s，而不只检查最终角度。
3. 旋钮从小强度开始做连续运行与 STOP/租约验证。持续检查 LINK_STATS、原始电流、板端时间、会话 ID 与错误记录。
4. 若失联重现，保留最后过程数据并停止扩大测试；需要继续分离板端 USB 状态、电源/EMI 与传感器时序问题。不能用抹掉错误弹窗或反复自动复位充当稳定运行。
