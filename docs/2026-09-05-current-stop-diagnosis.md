日期：2026-09-05。本次仅诊断，无电机动作命令、无大电流复现、未修改采样/保护代码。当前运行版本为刚烧录的 `0.5.0-output-haptic`；下列故障记录属于此前 `0.4.25-commissioned-36gp`，不能冒充新版本带载实测。

首次编码器故障后、软件重连前，仍有 **381 个 S 帧、跨度 3.8 s**，PWM 已归零、nFAULT=1，板端时间单调连续。随后 12:10:01 记录 `stop`、`OK stop`、`disconnected`、`connected`。这段没有串口 read/write 错误或启动横幅，不能称为“达到 1 A 就导致 USB 掉线”。网页恢复按钮确实会主动调用 disconnect/connect；具体是谁触发该请求没有 HTTP 请求来源记录。

停机后的遥测还出现短时负电流读数，例如 -5.498 A。它可能涉及制动/续流及采样瞬态，需要独立电流测量验证，不应直接认定为真实反向绕组电流峰值。暂不继续放大电流测试。

## 与当前代码对应

`firmware/src/main.cpp` 的 `cascadeControlTick()`：

1. 编码器随 500 Hz 速度采样读取，标称周期 2 ms；I2C 超时设置为 3 ms。
2. 新鲜度阈值是 `clamp(120000000 / max(|过滤速度|, |原始速度|), 2500, 10000)` µs，其中速度为后轴 °/s。高速下阈值接近 2.7–2.9 ms，采样时序余量较小。
3. 新鲜度检查位于本轮到期编码器读取之前；超时会 `motorStop()`，并非关闭 USB 或重启 MCU。
4. 电流模式没有“1 A 断串口”分支。新旋钮模式单独有 1.2 A 采样异常停机保护，仅对 `CONTROL_KNOB` 生效，不解释旧版 `CONTROL_CURRENT` 的两次故障。

过程表现是：空载电流目标增加 → 电机快速加速 → PWM 饱和、实际电流下降 → 后轴高速下允许的编码器间隔收紧 → 一次约 3.2 ms 的间隔触发停机。日志确定了触发链，但没有 I2C NACK、角度拒收和分段执行耗时计数，尚不能分辨迟到源于调度延迟、一次 I2C 失败还是电磁扰动。

`web/dashboard.js` 的异常恢复按钮对各种异常统一执行停止、断开、重连；这把控制保护恢复与 USB 链路修复混在了一起。`send()` 也把不同类型的失败统一显示为“通信失败”，需要按传输失败、命令拒绝、反馈保护分开呈现。

## 当前空闲链路检查

12:21 左右，COM23 身份仍为 `68EE8F52A79C`；正常回读 MODEL、CASCADE、DIAG、STATUS。最近 1987 帧跨度 19860 ms，按板端时间计算为 100 Hz，全窗 PWM=0、awake=0。该结果仅证明当前空闲通信正常，不能代替带载抗干扰验收。

## 建议的修复与验证顺序（尚未实施）

> 上述“当前”及本节“尚未实施”均指 12:21 的诊断时点。后续用户再次报告无回包后，已实施并烧录 0.5.1；见 [后续稳定性修复记录](2026-09-05-link-stability.md)。保留原始诊断，不把新的无回包事件归入旧版编码器停机。

1. 增加编码器传输失败/拒收计数和 ADC、I2C、控制周期最大间隔，持续记录断开前后数据与重启原因。
2. 单独设计更高频且有截止时刻保证的编码器采样路径，与 500 Hz 速度计算分开；校验高速角度跨圈边界。不能简单删除新鲜度保护或把阈值一律改到 10 ms。
3. UI 区分“电机因反馈超时停止”和“USB 真的掉线”；有持续遥测时不要用断开重连当作通用恢复动作。
4. 低能量验证之后再做受控电流阶跃；记录完整加速、停机和停机后至少 10 s 数据，验证限时停止、采样间隔、USB 连续性与制动电流。不能只看最终位置或仅凭编译通过宣布修复。
